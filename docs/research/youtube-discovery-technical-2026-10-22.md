# Техническая проверка поиска YouTube и оценки сложности

Дата: 22 октября 2026 года. Дополнение к [продуктовому исследованию](youtube-recommendations-2026-10-22.md). Это предложение архитектуры и результаты отдельного замера; поведение приложения и SPEC не менялись.

## Предлагаемая основа

Для поиска — YouTube Data API; для текста — сменяемый поставщик готовых субтитров; для лексической сложности — локальный spaCy и личный словарь; для ускорения повторных запросов — отдельный кэш кандидатов и анализа. Pydantic AI используется для разбора свободного запроса и необязательного тематического пояснения. Точное покрытие словарём вычисляет обычный код.

Основная проверяемая гипотеза: получение нескольких существующих дорожек и локальный анализ достаточно быстры для интерактивной выдачи. Надёжность получения дорожек по произвольным результатам поиска пока не установлена.

## Что проверено практически

Запущены текущие fetch_youtube_track, parse_track, EnglishAdapter.tokenize и vocabulary_features из локального окружения macOS. Версии: youtube-transcript-api 1.2.4, spaCy 3.8.11, en_core_web_sm 3.8.0. Сетевые запросы последовательные, одна попытка на ролик; кэш транскриптов не использовался. Загрузка NLP-модели при старте процесса заняла 0,199 с и вынесена из времени анализа.

Время получения включает перечисление дорожек, получение полного текста, преобразование в SRT и необязательный запрос названия через oEmbed. Нормализация дорожки заняла 0,2–6 мс. Для TED-выступления сбор счётчика лексем занял 5,34 мс, а повторный пересчёт по готовому счётчику и синтетическому профилю — медианно 0,075 мс за 100 повторов.

Последняя цифра измеряет только арифметику в памяти. Она не включает чтение профиля из базы, поиск, интерфейс или проверку качества. Реальный личный словарь не использовался и не изменялся. Проценты знакомости и CEFR для учащегося не вычислялись. Короткое видео Me at the zoo содержит меньше принятого минимального числа слов для категорической оценки.

Это три выбранных ролика, из которых два уже использовались в приёмке. Из результата нельзя вывести процент успешности по YouTube, p95 задержки или устойчивость под нагрузкой. Замер выполнялся на хосте, а не внутри Docker. Полнота дорожек не сверялась с аудио. [Машиночитаемые результаты и ограничения](youtube-discovery-probe-2026-10-22.json).

## Поиск кандидатов

Предлагаемый SearchIntent содержит query, target_language, duration_min/max, preferred_formats и effort. Свободную фразу разбирает агент Pydantic AI с ограниченной структурой результата. При явно заданных фильтрах этот вызов можно пропустить. LLM не создаёт идентификаторы видео.

Первый запрос выполняется к GET https://www.googleapis.com/youtube/v3/search с part=snippet, type=video, q, relevanceLanguage, videoCaption=closedCaption, videoEmbeddable=true, maxResults=25. На одну подборку сначала достаточно одной–двух поисковых формулировок; это предлагаемый лимит, не измеренный оптимум. Тему формулируем на изучаемом языке, например game design environmental storytelling вместо русского запроса.

relevanceLanguage задаёт предпочтение языка; closedCaption не гарантирует доступную оригинальную дорожку именно этого языка. Широкий videoDuration можно использовать для предварительного отбора. [Search: list](https://developers.google.com/youtube/data/reference/rest/v3/search/list).

Полученные ID передаются одним пакетным запросом GET https://www.googleapis.com/youtube/v3/videos с part=snippet,contentDetails,status. Длительность фильтруется точно, например 300–720 секунд; проверяются встраивание и ограничения региона, где доступны данные. defaultAudioLanguage используется как заявленный признак языка, а не доказательство выбранной озвучки. [Videos: list](https://developers.google.com/youtube/data/reference/rest/v3/videos/list), [схема видео](https://developers.google.com/youtube/data/reference/rest/v3/videos).

На 22 октября документация указывает 100 search.list вызовов в день в отдельном счётчике и 10 000 единиц для прочих методов, кроме videos.insert. При двух поисковых вызовах на подборку это до 50 новых подборок в день без дополнительных страниц и повторов. videos.list стоит одну единицу. Это расчёт по опубликованной квоте; фактическая квота конкретного проекта проверяется в его консоли. [Квоты](https://developers.google.com/youtube/data/determine_quota_cost).

В окружении и .env не обнаружены значения ожидаемых YOUTUBE_API_KEY, YOUTUBE_DATA_API_KEY или GOOGLE_API_KEY. Поэтому запрос официального поиска не выполнялся, его задержка и качество выдачи здесь не измерены. Для public search нужен ключ проекта с включённым API, хранимый на backend; OAuth аккаунта учащегося не нужен. [Настройка](https://developers.google.com/youtube/data/getting-started).

## Получение текста

Текущий [youtube.py](../../backend/app/youtube.py) уже перечисляет доступные дорожки, выбирает английский оригинал с приоритетом авторских субтитров и получает текст с временными метками. Библиотека не создаёт отсутствующий текст. Это объясняет, почему получение дорожки длинного видео может занимать меньше секунды: скачивается небольшой готовый текст. [README 1.2.4](https://github.com/jdepoix/youtube-transcript-api/blob/v1.2.4/README.md).

Для поисковых кандидатов предлагается контракт TranscriptProvider.get(video_id, target_language), возвращающий язык фактический, язык запрошенный, происхождение authored/automatic/asr/unknown, признак перевода, сегменты, источник и состояние полноты. Возвращённый язык проверяется явно. Если поставщик не сообщает происхождение, оно остаётся unknown. Пользовательский выбор аудиодорожки и дубляж требуют отдельной проверки согласованности.

Ошибки различаются как no_track, wrong_language, video_unavailable, temporarily_blocked, timeout и provider_error. Отсутствие дорожки не создаёт оценку уровня. При временном ограничении источника новые обращения приостанавливаются; готовые результаты остаются доступны. Ошибка одного кандидата не завершает подборку целиком.

| Источник | Возможность | Решение для прототипа |
| --- | --- | --- |
| youtube-transcript-api | Существующие авторские/автоматические дорожки без ключа; нет обещанной пропускной способности | Измерить текущий адаптер на более широкой выборке; ограничить число обращений и обработать ограничения |
| YouTube captions.download | Текст доступен при наличии права редактирования видео | Не обеспечивает текст произвольных чужих роликов. [Документация](https://developers.google.com/youtube/data/reference/rest/v3/captions/download) |
| Supadata | Готовые дорожки в native, генерация в generate, автоматическое переключение в auto | Возможный внешний адаптер; явно native и text=false; проверить response.lang. Новый ключ и отдельные расходы. [Документация](https://docs.supadata.ai/get-transcript) |
| GetYouTubeTranscript | Текст, caption_type, фактический язык, временные метки; пакет до 100 видео | Второй кандидат для сравнения поставщиков; запрос timestamps=true. [Документация](https://getyoutubetranscript.com/docs) |

Supadata: одна готовая дорожка — один кредит; генерация — два кредита за минуту; ответ 206 об отсутствии текста тоже расходует кредит. Поэтому двадцать имеющихся дорожек — 20 кредитов, а генерация двадцати десятиминутных видео — 400 кредитов. Бесплатный тариф даёт 100 кредитов в месяц и один запрос в секунду. Эти условия проверены по документации, платные вызовы не выполнялись. [Списание](https://docs.supadata.ai/get-transcript), [тарифы](https://supadata.ai/pricing).

GetYouTubeTranscript также документирует поиск по q/language/country и один кредит за страницу; это альтернативный поставщик поиска, который можно сравнить с официальным API. Заявленный batch сам по себе не гарантирует низкую задержку. Условия получения данных, успешность и независимость отказов от YouTube не подтверждены нашим тестом. [Документация](https://getyoutubetranscript.com/docs).

Распознавание звука — отдельный более тяжёлый путь. faster-whisper работает с доступным аудиофайлом, возвращает сегменты и может давать метки слов; само получение YouTube-аудио он не решает. В первой выдаче отсутствие готового текста оставляет кандидат без оценки. ASR можно исследовать для выбранного видео с подходящим источником аудио. [faster-whisper](https://github.com/SYSTRAN/faster-whisper).

Ни текущая библиотека, ни коммерческий API сами по себе не подтверждают разрешённость интеграции. YouTube API Policies ограничивают scraping и производные метрики из API Data. До поставки требуется определиться с подходящим источником текста и использованием данных. Технический замер не является такой проверкой. [Developer Policies](https://developers.google.com/youtube/terms/developer-policies).

## Быстрая оценка сложности

После нормализации сохраняются оригинальные реплики и привязка токенов ко времени. Кандидат получает словарную сигнатуру: счётчик (язык, лемма, часть речи), признаки автоматического исключения и частоты по временным окнам. При чтении профиля применяются знакомость, ignored, ручные исключения и существующие предварительные диагностические правила.

Алгоритм: суммировать частоты знакомых лексем, незнакомых и неоценённых; получить K, L, A и N; вычислить 100*K/N, 100*L/N и 100*A/N. Предварительные оценки маркируются отдельно. Число разных незнакомых слов и максимум нагрузки в окнах, например 30–60 секунд, дополняют среднюю оценку. Размер окна — проектный параметр для проверки.

Новые кандидаты не должны добавлять слова в личный словарь или создавать учебные материалы. Поэтому словарь загружается одним снимком и применяется в памяти. Нынешний KnowledgeService.get ожидает уже зарегистрированные лексемы и делает отдельные SQL-запросы; его правила следует выделить в общий чистый расчёт по ключу лексемы, сохранив ручные и диагностические приоритеты.

Сейчас импорт разбирает каждую реплику отдельно, а отбор лексики дополнительно разбирает текст целиком. Для поиска нужен общий анализатор: единый проход либо пакетная обработка через nlp.pipe с загруженной один раз моделью. Временные границы исходных реплик сохраняются. Изменение контекста может менять леммы и части речи: соответствие оценки поиска и открытого материала надо проверять, а затем переиспользовать одну версию анализа в обоих сценариях. [Рекомендации spaCy](https://spacy.io/usage/processing-pipelines).

Быстрый лексический расчёт уже технически доступен. Сертифицированный CEFR из этого не следует. В проекте частотный список 6000 единиц и небольшая диагностика — эвристики, что прямо указано в [описании данных](../../data/diagnostics/README.md). Если нужен именно CEFR-фильтр, потребуется размеченная выборка и калибровка отдельного оценщика. До этого можно показывать предварительную сложность относительно пользователя. Частотность, плотность слов и длина предложений без корректной пунктуации не дают доказанного уровня аудирования.

## Очередь, хранение и задержки

Начальный бюджет обработки: 25–50 результатов поиска, после фильтров 8–12 кандидатов на получение текста, до двух сетевых обращений одновременно. Это предлагаемые пределы для измерения. При необходимости следующая небольшая партия добирает варианты до пяти подходящих карточек. Общий предел времени, лимиты источника и отмена задачи ограничивают дальнейшую работу.

Текущие timeout=(4,8) в CaptionSession ограничивают отдельное соединение/чтение, а не весь подбор. Нужны также общий срок задачи и прекращение новых этапов после отмены; поток с уже начатым синхронным запросом не считается мгновенно остановленным. На локальном MVP достаточно одного процесса с ограниченной очередью и небольшим пулом сетевых задач. spaCy сейчас защищён общим Lock, поэтому увеличение числа потоков само по себе не ускорит NLP.

Предлагаемые слои кэша:

- Поиск: нормализованный запрос и фильтры, источник, время получения и срок обновления.
- Дорожка: video_id, фактический язык, источник, идентификатор дорожки при наличии, хеш текста.
- Анализ: хеш дорожки, версия языкового анализатора и правил отбора, частоты и временные признаки.
- Личная оценка: версия анализа плюс версия учебного профиля. При изменении знакомости пересчитывается только этот слой.

Для локального приложения достаточно отдельного SQLite-хранилища кандидатов рядом с текущей базой. Поиск не меняет библиотеку учащегося. Сроки хранения определяются источником; публичные метаданные YouTube обновляются или удаляются в пределах установленного 30-дневного ограничения. Временные ошибки кэшируются коротко и отдельно от подтверждённого отсутствия дорожки. [Правила хранения](https://developers.google.com/youtube/terms/developer-policies).

UI получает состояние задачи и готовые карточки постепенно, например через SSE. Карточки с непроверенным текстом явно остаются без личного процента; их позиция и объяснение обновляются после анализа. Первое отображение и готовность оценённых рекомендаций измеряются отдельно. Долгая дорожка не удерживает уже готовые результаты.

Цель для следующего эксперимента — первые оценённые варианты за 5–10 секунд и ограниченная обработка подборки за 15–20 секунд в обычном успешном случае. Это желаемый бюджет, не результат текущего замера. В него ещё входят неизвестные задержки Search API, разбора свободного запроса и отказов источников. Повторный запрос с готовыми текстами должен обходиться без сетевого получения дорожек и повторного NLP.

## Следующий технический эксперимент

Проверить реальную цепочку от Search API до первых пяти оценённых карточек на 20–30 видео, полученных по нескольким темам, с разными длительностями и типами субтитров. Зафиксировать долю успешных дорожек, неверный язык, ограничения воспроизведения, задержки каждого этапа, время первых результатов и всей подборки, расход квоты. Сравнить несколько последовательных и ограниченно параллельных запусков с учётом ограничений источника; отдельно измерить тёплый кэш.

Для поиска требуется ключ проекта. Для сравнения внешнего поставщика требуется его отдельное подключение; автоматически подключать платную генерацию при отсутствии дорожек не предлагается. После такого эксперимента можно обоснованно выбрать поставщика и задать ожидания скорости. Текущие три успешных получения уже подтверждают, что локальный анализ длинного текста не требует многосекундных LLM-вызовов.
